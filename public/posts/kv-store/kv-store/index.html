Why A KV-Store Project?#

In the modern era, there is a rising demand for edge computing — in many areas such as High Frequency Trading (HFT), performance and responsiveness are crucial. In this context, frequently storing and querying data to and from the database on a cloud server is not adequate due to transmission and operation overhead. Therefore, instead of using relational database, implementing a Key-Value Store system gains trend. This project is inspired by such trend, and aims to build a high-performance, thread-safe KV-Store system in C++, with extremely short and predictable query time.

Other than building the system itself, I would also like to make sure that the system is portable to other platforms and architectures, since in production environment we always assume that the runtime environment is heterogeneous. Therefore, after testing the system on my own machine (x86_64), I wrapped it up with Docker and implemented it on an EC2 instance (ARM) on AWS.

Architecture & Design#

Principle#

When it comes to key-value storage, one natural option would be to use a hash map (which corresponds to unordered_map in C++). While this might be a simple solution when the data size is relatively small, its performance will deteriorate when there is a huge amount of data rushing in. This is due to how hash map manages conflicts — when multiple data obtain the same key after hashing, they will be stored in the form of a linked list. When there are lots of conflicts, the linked lists become longer, and it takes $O(n)$ to go through the whole list. This not only damages the performance but also makes operation time unpredictable.

Another factor that will impact the execution time is the use of new and malloc in C++. These two operations call the memory allocator in the OS, which is out of control of our program, so the execution time of memory allocations is non-deterministic. Therefore, in this project I avoided using any raw memory allocations. Instead, the program will create a thread-local memory pool for each execution thread, which reserves a large chunk of memory upon construction and plays the roll of a memory allocator. We will go through the implementations in detail in the following sections.

Memory Pool#

This is the base component that provides the customized allocation and deallocation of memory. As is briefly mentioned before, the memory pool reserves a fixed chunk of bytes upon construction. The base of a memory pool is a vector of std::bytes. I use std::bytes as the data type because it is the best choice when it comes to raw memory management after its introduction in C++17 — it has a size of 8 bits, and it can prevent accidental arithmetic operations (the bit-wise operations are still allowed) unlike other data types such as char.

When it comes to allocating memories, one natural instinct would be to allocate memory based on the indices of the vector. However, this would soon become problematic when deallocations happen, since they are very likely to be random. After some random deallocations, if we perform another memory allocation, we would have to linearly probe through the vector to find the next available memory chunk. This would greatly hurt the performance of the system.

To solve this problem, I use a private member slot to keep track of the address of the next available memory chunk. When allocating a chunk of memory, we can directly allocate the memory address located in the slot; and when deallocating memory, we reverse the process. This is how we achieve this:

First, upon the construction of a memory pool, we chain the elements in the vector one after another. That is, the element at index 0 stores the address of that at index 1, the element at index 1 stores the address of that at index 2, and so on and so forth. Next, we let slot point to the element at index 0, indicating that this is the next available memory chunk.
